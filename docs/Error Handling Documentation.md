# Smart Spend Tracker API — документація OpenAPI та обробки помилок

## 1. Загальні відомості

- **Назва API:** Smart Spend Tracker API.
- **Версія:** 1.0.0.
- **Формат специфікації:** OpenAPI 3.0.4.
- **Файл специфікації:** `openapi.yaml`.
- **Технологія реалізації:** FastAPI.
- **Формат відповіді з помилкою:** `application/problem+json`.
- **Адреса локального сервера:** `http://localhost:8000`.
- **Автентифікація:** Bearer token для захищених ендпоїнтів. У поточній демонстраційній реалізації токен — `demo-token`.

Документація описує API на основі `openapi.yaml` і `main.py`. Важливо розрізняти **задекларовану відповідь OpenAPI** та **поведінку, фактично реалізовану в Python**. Деякі статуси включені до контракту для документування, але відповідний механізм у коді ще не реалізований.

## 2. Формат відповіді з помилкою

Помилки, оброблені спеціальними обробниками в `main.py`, повертаються з HTTP-заголовком `Content-Type: application/problem+json`.

| Поле | Тип | Обов'язковість | Призначення |
|---|---|---|---|
| `type` | string | Так | URI, що ідентифікує тип помилки. Формується на основі коду помилки. |
| `title` | string | Так | Коротка назва помилки. |
| `status` | integer | Так | HTTP-статус відповіді. |
| `code` | string | Так | Машиночитний код помилки. |
| `detail` | string | Так | Пояснення причини помилки. |
| `instance` | string | Так | Шлях запиту, на якому виникла помилка. |
| `traceId` | string | Так | Ідентифікатор для діагностики запиту. |
| `errors` | object | Ні | Деталі валідації, згруповані за полями. |
| `retryAfterSeconds` | integer | Ні | Кількість секунд, яку рекомендовано зачекати перед повторним запитом. |

Приклад відповіді 422:

```json
{
  "type": "https://api.smartspendtracker.com/errors/validation-failed",
  "title": "Помилка перевірки даних",
  "status": 422,
  "code": "VALIDATION_FAILED",
  "detail": "Одне або декілька полів не пройшли перевірку.",
  "instance": "/api/expenses",
  "traceId": "trace-a1b2c3d4e5f6",
  "errors": {
    "amount": ["Input should be greater than 0"]
  }
}
```

`traceId` генерується для кожної помилки. Точний текст елементів `errors` залежить від поля та правила валідації, яке було порушено.

## 3. Опис HTTP-помилок

### 3.1. 400 Bad Request — некоректний запит

**Значення:** запит має неправильний формат або не може бути оброблений у наданому вигляді.

**Задекларовано в OpenAPI:** відповідь із моделлю `ProblemDetails` та типом вмісту `application/problem+json`.

**Поточна реалізація:** у `main.py` немає окремого правила для 400. Якщо код підніме `HTTPException(400)`, загальний обробник поверне `code: HTTP_ERROR`, `title: Помилка запиту`, а `detail` буде сформовано з початкового `HTTPException.detail`. Тому спеціалізований код помилки 400 поки не реалізований.

### 3.2. 401 Unauthorized — користувач не автентифікований

**Причини:** заголовок `Authorization` відсутній або Bearer-токен недійсний.

Фактична відповідь використовує:
- `code`: `AUTHENTICATION_REQUIRED`;
- `title`: `Необхідна автентифікація`;
- `detail`: `Потрібно увійти в систему.`;
- HTTP-заголовок `WWW-Authenticate: Bearer`.

Приклад заголовка запиту:

```http
Authorization: Bearer demo-token
```

Токен демонстраційний. Реальна перевірка JWT не реалізована. Ендпоїнт входу наразі повертає токен, не перевіряючи пару email/пароль.

### 3.3. 403 Forbidden — доступ заборонено

**Значення:** користувач автентифікований, але не має дозволу на виконання операції.

Обробник підтримує такий статус і повертає:
- `code`: `RESOURCE_ACCESS_DENIED`;
- `title`: `Доступ заборонено`;
- `detail`: `Недостатньо прав для операції.`

**Обмеження:** у поточному `main.py` немає системи ролей чи перевірок дозволів, тому 403 задекларовано в контракті, але активні маршрути наразі не демонструють перевірки прав, яка генерувала б цю помилку.

### 3.4. 404 Not Found — ресурс не знайдено

**Фактичні сценарії в коді:**
- не знайдено витрату за `expenseId`;
- не знайдено категорію під час оновлення або видалення;
- під час створення витрати вказано категорію, якої немає;
- під час оновлення витрати вказано неіснуючу категорію.

Обробник повертає:
- `code`: `RESOURCE_NOT_FOUND`;
- `title`: `Ресурс не знайдено`;
- `detail`: `Запитаний ресурс не знайдено.`

Початковий текст `detail` з `HTTPException` замінюється загальним повідомленням.

### 3.5. 409 Conflict — конфлікт стану ресурсу

**Фактичний сценарій:** створення категорії з назвою, яка вже існує. Порівняння назв виконується без урахування регістру.

Обробник повертає:
- `code`: `RESOURCE_CONFLICT`;
- `title`: `Конфлікт`;
- `detail`: `Запит конфліктує з поточним станом ресурсу.`

**Обмеження:** під час оновлення категорії дублювання назви не перевіряється. Також код не перевіряє, чи використовується категорія витратами, перед видаленням.

### 3.6. 422 Unprocessable Content — помилка валідації

FastAPI/Pydantic повертає 422, якщо параметр шляху, query-параметр або тіло запиту не відповідають визначеним типам чи обмеженням.

| Поле | Правило валідації |
|---|---|
| `email` | Має бути коректною адресою електронної пошти. |
| `password` під час реєстрації | Від 8 до 128 символів. |
| `amount` | Число більше нуля. |
| `currency` | Рівно 3 символи. |
| `description` | Від 1 до 500 символів. |
| `date` | Коректна дата. |
| `categoryId` | UUID або `null`, якщо поле допускає `null`. |
| `limit` | Ціле число від 1 до 100. |
| `offset` | Ціле число, не менше 0. |
| `text` | Від 3 до 2000 символів. |
| `name` категорії | Від 1 до 80 символів. |

Для помилок автоматичної валідації фактичний обробник повертає `code: VALIDATION_FAILED`, `title: Помилка перевірки даних`, загальне поле `detail` і словник `errors`.

**Важлива відмінність:** коли перевірка `dateFrom > dateTo` викликає вручну `HTTPException(status_code=422)`, помилка проходить через обробник HTTP-помилок і отримує `code: HTTP_ERROR`, а не `VALIDATION_FAILED`.

### 3.7. 429 Too Many Requests — перевищення ліміту запитів

Обробник HTTP-помилок підтримує 429 і повертає:
- `code`: `RATE_LIMIT_EXCEEDED`;
- `title`: `Перевищено ліміт запитів`;
- `detail`: `Спробуйте пізніше.`;
- `retryAfterSeconds`: кількість секунд до повторної спроби.

Значення `retryAfterSeconds` береться із заголовка `Retry-After`; якщо заголовок відсутній або не містить цілого числа, використовується 60 секунд.

**Обмеження:** механізм rate limiting, який автоматично обмежує частоту запитів, у наданому `main.py` не налаштований. Отже, формат відповіді обробляється, але саме обмеження запитів ще не реалізоване.

### 3.8. 500 Internal Server Error — внутрішня помилка сервера

OpenAPI описує 500 як можливу відповідь сервера. У поточному `main.py` немає загального обробника неочікуваних винятків, який гарантував би для всіх таких випадків тіло `ProblemDetails`. Тому фактичне тіло 500 може відрізнятися від задекларованого формату.

### 3.9. 503 Service Unavailable — сервіс недоступний

**Фактичні сценарії:**
- `POST /api/expenses/natural-language` повертає 503, оскільки AI-сервіс не налаштований;
- `POST /api/expenses/{expenseId}/classify` повертає 404, якщо витрату не знайдено, і 503, якщо витрата існує, але AI-сервіс не налаштований.

Обробник повертає:
- `code`: `SERVICE_UNAVAILABLE`;
- `title`: `Сервіс недоступний`;
- `detail`: `Необхідний сервіс тимчасово недоступний.`

Поточний код не встановлює заголовок `Retry-After` автоматично для 503.

## 5. Детальний опис доданих ендпоїнтів

### 5.1. `PUT /api/categories/{category_id}` — оновлення категорії

**Призначення:** оновити назву та колір категорії.

**Параметр шляху:**
- `category_id` — рядок, ідентифікатор категорії. У реалізації Python він типізований як `str`, а не UUID.

**Тіло запиту:**

```json
{
  "name": "Продукти",
  "color": "#4F46E5"
}
```

**Відповіді:**
- `200 OK` — повертає оновлену категорію;
- `401 Unauthorized` — токен відсутній або недійсний;
- `404 Not Found` — категорію з указаним ID не знайдено;
- `422 Unprocessable Content` — тіло запиту не пройшло валідацію;
- `500 Internal Server Error` — внутрішня помилка сервера, задекларована в OpenAPI.

У поточному коді не перевіряється унікальність назви під час оновлення категорії.

### 5.2. `DELETE /api/categories/{category_id}` — видалення категорії

**Призначення:** видалити категорію за її ідентифікатором.

**Параметр шляху:** `category_id` — рядок, ідентифікатор категорії.

**Відповіді:**
- `200 OK` — категорію видалено;
- `401 Unauthorized` — токен відсутній або недійсний;
- `404 Not Found` — категорію не знайдено;
- `500 Internal Server Error` — внутрішня помилка сервера, задекларована в OpenAPI.

Приклад успішної відповіді:

```json
{
  "message": "Category deleted successfully"
}
```

Ендпоїнт повертає **200**, а не 204. Перед видаленням код не перевіряє, чи пов'язані з категорією наявні витрати.

### 5.3. `GET /api/health` — перевірка доступності API

Ендпоїнт не потребує токена. У разі успіху повертає `200 OK`:

```json
{
  "status": "ok"
}
```

## 6. Обробники помилок у `main.py`

### `HTTPException`

Функція `handle_http_error()` перехоплює `HTTPException` і повертає JSON у форматі `application/problem+json`. Для статусів 401, 403, 404, 409, 429 і 503 визначені окремі коди та повідомлення. Для інших статусів застосовується загальний код `HTTP_ERROR`. Заголовки початкового винятку зберігаються.

### `RequestValidationError`

Функція `handle_validation_error()` обробляє помилки автоматичної перевірки параметрів і моделей. Вона повертає HTTP 422 з кодом `VALIDATION_FAILED` і об'єктом `errors`, де повідомлення згруповані за полями.

## 7. Відомі обмеження реалізації

1. **Демонстраційна автентифікація:** `/api/auth/login` не перевіряє пароль і email, а повертає демонстраційний токен.
2. **Доступ:** у коді немає повноцінної системи ролей та дозволів, хоча 403 описано в OpenAPI.
3. **400:** немає спеціального коду `BAD_REQUEST`; загальний обробник використовує `HTTP_ERROR`.
4. **409:** фактично перевіряється дублювання назви тільки під час створення категорії.
5. **422:** автоматичні помилки валідації мають `VALIDATION_FAILED`, але вручну піднятий `HTTPException(422)` має `HTTP_ERROR`.
6. **429:** обробник існує, але обмеження частоти запитів не налаштоване.
7. **500:** немає загального exception handler, який гарантує однакове тіло помилки для всіх неочікуваних винятків.
8. **503:** функції AI-класифікації та розпізнавання тексту наразі не підключені.
9. **Зберігання:** витрати та категорії зберігаються в оперативній пам'яті, а не в постійній базі даних.
10. **OpenAPI та Swagger UI:** окремий `openapi.yaml` не оновлює автоматично `/docs`; FastAPI генерує вбудовану схему з Python-коду.

## 8. Перегляд документації у Swagger

Щоб запустити API:

```bash
python -m uvicorn main:app --reload
```

Після запуску відкрийте `http://127.0.0.1:8000/docs`.

FastAPI генерує цю сторінку на основі маршрутів і моделей у `main.py`. Щоб переглянути саме зовнішній `openapi.yaml`, його можна відкрити у Swagger Editor або налаштувати застосунок на використання цієї специфікації. Для уникнення розбіжностей потрібно підтримувати YAML і Python-код синхронізованими.

## 9. Висновок

Специфікація `openapi.yaml` описує 16 операцій API, спільну модель `ProblemDetails` та відповіді з помилками. До неї включено `PUT /api/categories/{category_id}`, `DELETE /api/categories/{category_id}` і `GET /api/health`, які були відсутні в початковому YAML, але присутні в Python-коді. ## 5. Детальні приклади помилок для 10 API та реакція клієнта

У прикладах нижче `http://localhost:8000` — базова адреса сервера. Усі `traceId` та UUID є демонстраційними. Фактичний `traceId` генерується сервером і буде іншим у кожній відповіді. Точний текст повідомлень Pydantic у полі `errors` може дещо відрізнятися залежно від версії бібліотеки.

### Загальні правила обробки помилок на клієнті

1. Спочатку перевіряти **HTTP-статус**, потім читати `code` і `errors`. Не визначати тип помилки лише за текстом `detail`.
2. Для `422` показувати помилку біля відповідного поля форми; не повторювати той самий запит, доки дані не виправлені.
3. Для `401` попросити користувача увійти повторно або отримати токен і повторити запит один раз після оновлення авторизації. Не запускати нескінченні повтори.
4. Для `403` повідомити про відсутність дозволу; не повторювати запит без зміни прав.
5. Для `404` повідомити, що ресурс не знайдено, і оновити локальний список/стан. Не повторювати той самий запит без зміни ідентифікатора.
6. Для `409` повідомити про конфлікт і запропонувати змінити дані.
7. Для `429` чекати `retryAfterSeconds` або заголовок `Retry-After`; не повторювати запит у циклі.
8. Для `503` показати тимчасову недоступність функції; дозволити користувачу повторити пізніше. Не створювати вигляд, що операція виконана.
9. Перед показом помилки перевіряти, що тіло відповіді справді є JSON. Неуспішна відповідь від проксі чи сервера може мати інший формат.
10. За потреби передавати `traceId` до журналу клієнта або служби підтримки. Не показувати користувачу внутрішні технічні подробиці замість зрозумілого повідомлення.

### API 1. Реєстрація — `POST /api/auth/register`

**Ситуація:** клієнт надсилає некоректну електронну адресу або занадто короткий пароль. `email` має бути коректною адресою, `password` — від 8 до 128 символів.

Запит:

```http
POST /api/auth/register HTTP/1.1
Host: localhost:8000
Content-Type: application/json
```

```json
{
  "email": "not-an-email",
  "password": "123"
}
```

Очікувана помилка: **HTTP 422 Unprocessable Content**.

```json
{
  "type": "https://api.smartspendtracker.com/errors/validation-failed",
  "title": "Помилка перевірки даних",
  "status": 422,
  "code": "VALIDATION_FAILED",
  "detail": "Одне або декілька полів не пройшли перевірку.",
  "instance": "/api/auth/register",
  "traceId": "trace-a1b2c3d4e5f6",
  "errors": {
    "email": ["value is not a valid email address"],
    "password": ["String should have at least 8 characters"]
  }
}
```

**Реакція клієнта:** залишити користувача на формі реєстрації; показати повідомлення біля `email` і `password`; зберегти введені значення, щоб їх не довелося вводити повторно; не повторювати запит автоматично. Формулювання всередині `errors` потрібно вважати прикладом, оскільки воно залежить від версії Pydantic.

### API 2. Вхід — `POST /api/auth/login`

**Ситуація:** поле `email` має некоректний формат. Навіть якщо пароль правильний, запит не пройде валідацію email.

Запит:

```http
POST /api/auth/login HTTP/1.1
Host: localhost:8000
Content-Type: application/json
```

```json
{
  "email": "user-at-example",
  "password": "password123"
}
```

Очікувана помилка: **HTTP 422**, `code: VALIDATION_FAILED`.

```json
{
  "type": "https://api.smartspendtracker.com/errors/validation-failed",
  "title": "Помилка перевірки даних",
  "status": 422,
  "code": "VALIDATION_FAILED",
  "detail": "Одне або декілька полів не пройшли перевірку.",
  "instance": "/api/auth/login",
  "traceId": "trace-b2c3d4e5f6a7",
  "errors": {
    "email": ["value is not a valid email address"]
  }
}
```

**Реакція клієнта:** показати «Введіть коректну адресу електронної пошти»; не очищати поле пароля без потреби; дозволити повторне надсилання після виправлення адреси. **Обмеження реалізації:** зараз `login` не перевіряє фактичну пару email/пароль і повертає демонстраційний токен, тому приклад описує валідацію формату, а не відмову через неправильний пароль.

## 6. Що важливо для реалізації клієнта

- `401`, `403`, `404`, `409` та `503` у поточному коді повертають стандартизований об'єкт `ProblemDetails`, але `detail` для цих статусів є загальним і може не містити початкову причину з маршруту.
- `422`, що виникає під час автоматичної перевірки Pydantic, містить `errors` із назвами полів. Натомість ручний `HTTPException(status_code=422)` для некоректного діапазону дат повертає `code: HTTP_ERROR` без `errors`.
- `429` описаний у обробнику, але автоматичне обмеження частоти запитів у наданому `main.py` не налаштоване. Клієнт має підтримувати `retryAfterSeconds`, однак не слід вважати, що поточна демоверсія реально генеруватиме 429.
- `403` також задекларований, але перевірки ролей/прав у поточній реалізації не показані.
- `500` описаний у специфікації, проте загальний обробник неочікуваних винятків, який гарантував би формат `ProblemDetails`, у `main.py` відсутній.
- Токен `demo-token` і тимчасові словники `expenses` та `categories` призначені для демонстрації. Дані зберігаються в пам'яті процесу, а реальна автентифікація та постійне сховище не реалізовані.
